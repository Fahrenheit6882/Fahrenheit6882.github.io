## Project Overview

**Fahrenheit Robotics** is the public website and knowledge base for FIRST Robotics Team 6882 (Fredericksburg area). It serves two audiences:

- **Public visitors** — team info, contact, social links (root `index.html`)
- **Team members** — guides on software, mechanical, CAD, project management, and website development (Docusaurus docs site at `/site/`)

Live site: https://fahrenheitrobotics.org

Sidebar is **auto-generated** from the folder structure (`sidebars.ts` uses `autogenerated`). Control order and labels via front matter:

```yaml
---
sidebar_label: My Label

```

### Project sub-sites (`docs/projects/<name>/`)

A team project with public-facing docs (parts, build, troubleshooting) uses several audience-specific pages rather than one long doc. The pattern established for `projects/pumpkinator/`:

| Page | Audience | Content |
|---|---|---|
| `overview.md` | Anyone (QR-code landing target) | Quick summary + links out to the pages below |
| `troubleshooting.md` | Someone who already has a built/assembled unit | Symptom → cause → fix, no assumed technical background |
| `preparation-steps.md` | The mentor prepping kits ahead of time | Batch soldering/crimping tasks that produce reusable sub-harnesses |
| `assembly-steps.md` | Students, given an already-prepped kit | Lighter steps that plug prepped harnesses together, with test checkpoints at each stage |
| `light-and-sound-shows.md` | Anyone loading or changing the code and sounds | Arduino IDE setup, uploading `pumpkin.ino`, and copying MP3s onto the JQ6500 (Windows only) |

Not every project needs all of these. Add pages as the project's documentation needs grow. Keep `sidebar_position` values sequential so the sidebar order matches the order a reader would actually use them in.

## Key Configuration Files

- **`site/docusaurus.config.ts`** — site title, URL, navbar, footer, theme, plugins
- **`site/sidebars.ts`** — sidebar structure (currently auto-generated)
- **`site/src/css/custom.css`** — theme color overrides (primary green: `#2e8555` light / `#25c2a0` dark)
- **`site/src/pages/index.tsx`** — redirects Docusaurus root → `/site/docs/welcome`
- **`CNAME`** — domain config (`fahrenheitrobotics.org`)

The Docusaurus site is served at the `/site/` base path (not `/`). The root `/` is the standalone `index.html` landing page.

### Custom standalone pages (`site/src/pages/*.tsx`)

Any file under `site/src/pages/` becomes a route at `/site/<filename>`, separate from the docs. These are plain React, not MDX, so they can skip the docs `Layout` (no navbar/footer) for a fully custom design, for example a marketing/landing page meant as a QR-code target on a printed sticker. See `pumpkinator.tsx` + its `pumpkinator.module.css` for the established pattern: a dark, illustrated one-pager with its own nav, hero, and CTA cards linking into the relevant `docs/projects/<name>/` pages. Load Google Fonts via `<Head>` from `@docusaurus/Head` rather than editing the global config, so the font only loads on that page.

## Deployment Process (Manual)

Deployment is currently **manual** (no CI/CD yet — it's a tracked TODO in CHANGELOG.md). Use the `deploy-website` skill (see below) to run this — it was tested end-to-end and confirmed live on 2026-08-23 (tag `1.5.1`).

1. On `docusaurus`, working tree clean, push the branch too: `git push origin docusaurus`
2. Build: `./scripts/deploy0.sh` (runs `yarn && yarn build` inside `site/`)
3. Stage: `./scripts/deploy1.sh` — copies `site/build/`, `img/`, `index.html`, `app.css`, `README.md`, `CHANGELOG.md` into `../temp-site` (sibling dir, outside git)
4. Switch to `main` and fast-forward it: `git checkout main && git pull --ff-only origin main` — local `main` is rarely checked out and gets stale, always sync before replacing files
5. **`scripts/deploy2.sh` only exists on `main`** (it excludes itself from its own replace-list so it survives every deploy — it doesn't exist on `docusaurus`). Bump the `TAG` variable inside it to the next version, then run it — it swaps in the staged `site/`, `img/`, `index.html`, `app.css`, `README.md`, `CHANGELOG.md`
6. Commit, push, and tag:
   ```bash
   git add -A
   git commit -m "Deploying version $TAG"
   git push origin main
   git tag $TAG
   git push origin $TAG
   ```
7. Return to work: `git checkout docusaurus`
8. Verify live: GitHub Pages takes a minute or two to propagate. Poll a newly-added file (e.g. `curl -o /dev/null -w '%{http_code}' https://fahrenheitrobotics.org/img/<new-file>`) until it 200s, then ask the human to hard-refresh and visually confirm — origin catching up doesn't always mean the CDN edge has too.

See `site/docs/marketing/website/website-deploy.md` for the full step-by-step guide.

### Known deploy gotchas

The `site/` directory holds different things depending on which branch is checked out (Docusaurus source on `docusaurus`, the built static output on `main`), but it's the same physical folder on disk. Two things from that can trip up step 5 (`deploy2.sh`'s `rm -rf site/`):

- **Leftover `node_modules`/`build`/`.docusaurus`.** Running `yarn`/`yarn build` while on `docusaurus` creates these inside `site/`; they're gitignored, so switching to `main` doesn't remove them. `rm -rf site/` then fails (`Directory not empty` or similar) partway through, and the following `mv $TEMP_SITE/site site` nests the new build inside the old folder as `site/site/` instead of replacing it. Fix: before running `deploy2.sh`, clear them proactively: `rm -rf site/node_modules site/build site/.docusaurus`.
- **A running dev server.** If `yarn start` / `docusaurus start` is active against `site/` (yours or the human's, in another terminal), it holds file locks and `rm -rf site/` fails with `Device or resource busy`. Ask the human to stop it before continuing.
- **If `site/site/` happens anyway**, don't retry `rm -rf site/` blindly. Move the new content up instead (`shopt -s dotglob` first, so hidden files like `.nojekyll` aren't skipped), then remove the now-empty `site/site/`.

## Homepage Slideshow (`index.html`)

The landing page has a plain-JS carousel (`.mySlides` divs near the top of `index.html`). Use the `add-slideshow-photo` skill to add new photos — it encodes what we worked out below.

- **Naming**: `img/slide_<short_description>.jpeg` — lowercase, underscore-separated.
- **Sourcing**: photos usually come from a Google Photos share link (right-click a photo → "Copy image address" → a `lh3.googleusercontent.com/...` URL) which can be `curl`'d directly; verify the download is actually an image (`file -b --mime-type`) before using it, since expired/malformed links return an HTML error page instead.
- **Target sizes** — every slide must render at the **same height**, so orientation determines the target:
  | Orientation | Crop/resize to | `<img>` inline style |
  |---|---|---|
  | Landscape/square | **1200×600** (2:1) | `style="width:100%"` |
  | Portrait | **400×600** (2:3) | `style="width:33.33%"` |

  Center-crop to the target aspect ratio first (`sips -c <h> <w>`), then resize exactly (`sips -z <h> <w>`) so nothing gets distorted.
- **Why 33.33% for portrait, not 100%**: all slides use `width:100%` of the same container and no fixed height, so display height is driven entirely by the image's own aspect ratio at that width. A 2:1 landscape image at 100% width renders at height = 0.5 × container width. A 2:3 portrait image at 100% width would render 3× as tall (height = 1.5 × container width) — visibly blowing up the carousel on that slide. Scaling portrait images down to 33.33% width makes their rendered height match the landscape slides exactly (the math: target height ÷ 1.5 aspect = 1/3 of container width).

## Things to Know

- **Do not modify `index.html` or `app.css`** for doc content changes — those files belong to the separate landing page, not the Docusaurus site.
- **Images in docs** live in `img/` subdirectories alongside the `.md` files and are referenced relatively (e.g., `![alt](img/foo.png)`).
- **Images in static/** (`site/static/img/`) are for assets referenced from config or components.
- The `site/build/` directory is gitignored — it is the Docusaurus build output.
- A `.nojekyll` file at the repo root disables Jekyll processing on GitHub Pages.
- Docusaurus version is **3.x** — use v3 docs, not v2.
- **QR code assets** (`site/static/img/pumpkinator-qr.png`, `pumpkinator-qr-sheet.png`/`.pdf`) were generated by a one-off Node script (`qrcode` + `sharp`, verified by decoding the result back with `jsqr`), not by anything in this repo's build. Regenerate the same way if the target URL or branding ever changes: build the QR at high error-correction (`H`), composite a logo badge sized under ~15% of the code's area so it still decodes, and verify the output actually decodes before using it.
